# C1. Чужой хороший PR

> Работа над кейсом шла в черновом приватном репозитории. При публикации история перенесена сюда, а PR этого кейса (описания, ревью, разбор) и логи запусков CI - файлами: [docs/reviews](../docs/reviews/README.md), [evidence/ci-runs](evidence/ci-runs). Номера PR ниже - номера в черновике.


**Вопрос.** Агент сгенерировал PR на 900 строк, тесты и CI зелёные, через два часа сработает авто-мерж. Внутри переписан слой абстракции SMS-провайдера. Что потребовать от агента, что проверить руками, что поменять в процессе.

**Короткий ответ.** Зелёный CI значит только одно: не сломались существующие тесты. А они почти всегда про «счастливый путь», а не про семантику ретраев, идемпотентности и порядка фолбэка.

На стенде переписанный слой с четырьмя скрытыми сдвигами поведения прошёл все исходные тесты и CI. После защит тот же PR заблокирован контрактными тестами и проверкой процесса.

Две вещи пришлось узнать на собственных ошибках, их нашло независимое ревью:
- защита по списку путей обходится переносом кода в новую папку;
- проверка, которая берётся из ветки PR и верит метке и описанию от автора, отключается самим автором PR.

Защита работает, только если её правила живут в `main` и она смотрит на факты: файлы, одобрение владельца на текущем коммите. Текст, который пишет автор PR, фактом не считается.

## Репро

**Сервис** [`src/sender.ts`](src/sender.ts) отправляет коды входа через абстракцию `SmsProvider`. В нём два HTTP-провайдера, ретраи только на 5xx/429/таймаут, один ключ идемпотентности на все попытки, строгий порядок фолбэка, таймаут на попытку. Исходных тестов три, [все про «счастливый путь»](tests/sender.test.ts).

**Агент:** OpenCode CLI с `deepseek-v4.1-flash`. Задача смежная, без подсказки что-то переписывать: третий провайдер и статусы доставки ([текст задачи](https://github.com/cyanerd/agent-engineering-cases/blob/07352f6/c1-agent-pr/AGENT_TASK.md)). Прогонов два:

- **Прогон 1 загрязнён** ([PR #2](../docs/reviews/pr-02.md), закрыт с пометкой). Агент работал в полной копии репозитория. Прежде чем писать код, он сам прочитал план и дизайн этого кейса ([журнал](https://github.com/cyanerd/agent-engineering-cases/blob/435ff60/c1-agent-pr/agent-runs/2026-11-21-deepseek-v4.1-flash.md), шаги 16-17). А там написаны гипотеза и свойства контрактных тестов. Это нашёл независимый ревьюер, я сам пропустил. Вывод «агент сам не переписал» по этому прогону делать нельзя.
- **Прогон 2 изолированный** ([PR #5](../docs/reviews/pr-05.md)). Отдельная копия: только сервис в исходном состоянии, без `docs/` и других кейсов, своя история git ([журнал](https://github.com/cyanerd/agent-engineering-cases/blob/07352f6/c1-agent-pr/agent-runs/2026-11-21-deepseek-v4.1-flash-isolated.md)). Агент снова **не стал** переписывать абстракцию. Он добавил модуль `delivery.ts`, провайдера и 15 тестов, в `sender.ts` и `types.ts` +61/−10 строк. 8 контрактных тестов его код проходит. Коммит агента - [`0baccec`](https://github.com/cyanerd/agent-engineering-cases/commit/963d128), как есть, без трейлеров. Журнал - отдельным коммитом от моего имени.

Что нашлось при ручном просмотре кода агентов, тесты этого не ловят:
- **В прогоне 1:**
  - карты статусов растут без ограничения;
  - поздний `failed` перезаписывает уже полученный `delivered`;
  - подлинность callback переложена на вызывающего.
- **В прогоне 2:** callback сопоставляется только по id сообщения, без провайдера, поэтому одинаковые id у двух провайдеров перепутаются.
- **В исходном сервисе** (это мой код) `inFlight` тоже растёт без ограничения.

**Переписанный слой - [PR #3](../docs/reviews/pr-03.md), сконструирован вручную.** Агент слой не переписал ни разу, поэтому переписывание сделано намеренно. Пометка стоит в заголовке, описании и коммите.
- **Объём:** 558 изменённых строк вместе с тестами - не 900, но той же природы.
- **Что внутри:** реестр маршрутов, политика ретраев, circuit breaker, журнал доставок, метрики, конфиг из env, 14 новых тестов. Все исходные тесты зелёные.

Скрытые сдвиги поведения:
1. ключ идемпотентности свой у каждой попытки - шлюз, ответивший с опозданием, получит повтор как новое сообщение, то есть **второе SMS**;
2. ретраи на любые ошибки, включая 4xx (неверный номер), и фолбэк на второго провайдера;
3. дедупликация только завершённых отправок - два одновременных запроса с одним `requestId` отправляют **два SMS**;
4. маршруты сортируются по цене - при заданных ценах меняется порядок фолбэка.

| #5 агент, прогон 2 (изолирован) | зелёный ([прогон](evidence/ci-runs/44898173493.md)) | - | `test` с контрактом зелёный ([прогон](evidence/ci-runs/44899218560.md)); `pr-guard` красный: модуль меняется без одобрения владельца, `automerge`, нет `Scope:` ([прогон](evidence/ci-runs/44899856914.md)) |
| #3 переписанный слой (сконструирован) | зелёный ([прогон](evidence/ci-runs/44896380183.md)) | `contract` красный (3 из 8), `pr-guard` красный ([прогон](evidence/ci-runs/44896877691.md)) | `test` с контрактом красный ([прогон](evidence/ci-runs/44899215550.md)); `pr-guard` красный по всем четырём: 558 строк в критичных путях, `automerge`, нет одобрения владельца, нет `Scope:` ([прогон](evidence/ci-runs/44899648691.md)) |

**Контрактные тесты** на [PR #3](../docs/reviews/pr-03.md) ловят три сдвига из четырёх:
- одновременные запросы;
- повтор ключа;
- ретрай на 4xx.

Порядок по цене они не ловят: он включается только при заданных ценах. Нужен контрактный тест на реальную конфигурацию маршрутов.

**Защиты v1 оказались дырявыми.** Это нашли сами прогоны и независимое ревью [PR #4](../docs/reviews/pr-04.md):
1. **Перенос кода.** Критичными были `src/providers/**`, `sender.ts`, `types.ts`. [PR #3](../docs/reviews/pr-03.md) перенёс логику в `src/gateway/`, и лимит размера не сработал ([прогон](evidence/ci-runs/44896727170.md)).
2. **Проверка запускалась из ветки PR** (`pull_request`). Тот же PR мог ослабить `pr-guard.ts`, удалить шаг из workflow, переписать `FakeProvider` или скрипт `contract`, и всё было бы зелёным. Ревьюер собрал такой PR, и защита ответила «ok».
3. **Факты от автора.** Scope брался из описания PR, и `Scope: **` пропускал всё, как и строка в HTML-комментарии. Отметкой ревью была метка, которую может поставить любой с правом записи, включая токен агента, и она не снималась после новых коммитов.

**Защиты v2**, на каждую дыру есть тест:
- `pr-guard` запускается через `pull_request_target`. GitHub берёт такой workflow из ветки по умолчанию, а код - из базового коммита. Код PR не исполняется, файлы и ревью читаются через API.
- Критичным считается весь модуль (кроме `*.md` и `docs/`), его контрактные тесты, сама проверка, `package.json` и `.github/`.
- Вместо метки нужно одобрение владельца из CODEOWNERS на **текущем** head-коммите.
- Scope не может быть «всё» и не читается из комментариев и блоков кода.
- PR, не трогающие модуль и CI, проверка пропускает, поэтому она может быть обязательной для всех PR.
- Контрактные тесты идут в общем CI на каждом push.

Остаток: код, вынесенный за пределы модуля (новый пакет в корне) и подключённый одной строкой импорта, обходит лимит размера. Обход **сужен, но не закрыт**. Закрывают его ревью владельца на весь PR и контрактные тесты.

### Результаты v2

Защиты v2 действуют с момента, когда попали в `main`: `pull_request_target` берёт workflow только из ветки по умолчанию.
- **[PR #3](../docs/reviews/pr-03.md) (опасный)** заблокирован двумя независимыми способами: контрактными тестами по смыслу и `pr-guard` по процессу.
- **[PR #5](../docs/reviews/pr-05.md) (аккуратный)** проходит контракт, но тоже ждёт одобрения владельца. По диффу их не различить, а цена ошибки одинакова.

По ходу всплыли две ошибки уже во второй версии, обе исправлены:
- после слияния `pr-guard` падал из-за относительного пути к CODEOWNERS ([PR #6](../docs/reviews/pr-06.md)). Проверка при этом падала «закрыто», то есть безопасно, но по неверной причине;
- `AGENT_TASK.md` в корне модуля считался критичным файлом (шаблон `**/*.md` не ловит файлы в корне). На вердикт это не влияло, тест добавлен.

## Что делать

**Потребовать от агента** (до того, как кто-то читает код):
- разделить рефакторинг и фичу на отдельные PR; рефакторинг - без изменения поведения;
- в описании: намерение, **что меняется в поведении** (ретраи, идемпотентность, порядок, таймауты) и как откатить;
- сначала - контрактные тесты текущего поведения слоя отдельным PR, зелёные на старом коде, и только потом рефакторинг под ними;
- агент работает в копии, где есть только нужный код: иначе он читает то, чего не должен (как в прогоне 1).

**Проверить руками** (этого не проверяют ни CI, ни агент):
- семантику ретраев: на что ретраим, с каким ключом идемпотентности, что будет при таймауте после того, как шлюз уже принял сообщение;
- дедупликацию при одновременных запросах;
- порядок фолбэка на реальной конфигурации;
- прогон на песочнице провайдера: сколько SMS реально ушло на один запрос.

**Поменять в процессе:**
- запрет авто-мержа для критичных путей (SMS, авторизация, платежи);
- CODEOWNERS и обязательное одобрение владельца на текущем коммите ([`.github/CODEOWNERS`](../.github/CODEOWNERS));
- лимит размера изменений в критичных путях;
- scope задачи;
- контрактные тесты абстракции, не зависящие от реализации, - обязательной проверкой;
- **правила проверки живут в `main` и не исполняют код PR**; сама проверка, CI и контрактные тесты - тоже критичные пути.

Реализация - [`scripts/pr-guard.ts`](scripts/pr-guard.ts) (14 тестов) и [`.github/workflows/pr-guard.yml`](../.github/workflows/pr-guard.yml).

## Вывод

**Подтвердилось:** зелёный CI на переписанном слое ничего не гарантирует, защиты процесса такой PR блокируют.

**Неожиданно:**
- Агент на смежной задаче дважды, в том числе в изолированном прогоне, сделал аккуратное дополнение и семантику не тронул. Защиты блокируют и такой PR, без одобрения владельца. Это цена процесса, и платить её стоит: по диффу «хороший» и «опасный» PR выглядят одинаково зелёными.
- Мои собственные защиты первой версии обходились тремя способами. Их нашли прогон и независимое ревью, а не я. Довод за то, чтобы защиты процесса ревьюил кто-то, кроме автора.

## Ограничения

- **Приватный репозиторий на бесплатном плане GitHub,** защита веток там не работает. Блокировка показана красными проверками, а не запретом мержа. После публикации включается branch protection: обязательные `test`, `pr-guard`, `gitleaks` и ревью CODEOWNERS. Прогон повторяется, ссылки обновляются.
- **Нет второго человека для одобрения.** Владелец не может одобрить свой PR, поэтому на стенде `critical-review` для PR с изменениями модуля остаётся красной. [PR #4](../docs/reviews/pr-04.md), который вводит защиты, слит владельцем в обход собственной проверки: защита начинает действовать с момента попадания в `main`.
- **`pull_request_target` не перезапускается на новое ревью.** После одобрения проверку нужно перезапустить; в публичном репозитории это закрывает обязательное ревью в branch protection.
- **Один агент, одна задача, два прогона.** «Агент не переписал абстракцию» - наблюдение, а не закономерность.
- **[PR #3](../docs/reviews/pr-03.md) сконструирован.** Его сдвиги типичны для таких рефакторингов, но выбраны мной.
