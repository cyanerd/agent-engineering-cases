# 03 B1 Один телефон - пять компаний - Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Стенд Keycloak + Postgres + API, на котором шесть сценариев «один номер - пять юрлиц» воспроизводимо ломаются на наивной модели и проходят на исправленной; схемы данных для отчёта.

**Architecture:** `b1-phone-orgs/`. docker compose: Postgres 16 (схемы `keycloak` и `app`), Keycloak (последняя версия, образ закреплён по digest) с собственным расширением `keycloak-sms` (Java 21, Maven): эндпоинт выдачи SMS-кода и аутентификатор для direct grant по `phone` + `code`. Два realm: `naive` и `fixed`, режим аутентификатора задаётся атрибутом realm. API на TS (node:http + `jose`) с двумя наборами правил (naive/fixed) поверх одной базы `app`. Сценарии - vitest против поднятого стека.

**Tech Stack:** Docker Compose, Keycloak + Java SPI (Maven), Postgres 16, TypeScript, `pg`, `jose`, vitest.

**Spec:** `docs/superpowers/specs/2026-11-21-cases-design.md`, раздел «B1. Один телефон - пять компаний».

## Global Constraints

- Вход - только через Keycloak (токен выдаёт Keycloak, API проверяет подпись по JWKS). Ничего из рабочих репозиториев Keycloak/SMS не копировать; расширение пишется с нуля по публичной документации SPI.
- SMS - заглушка: код пишется в «outbox» расширения, читать его может только стенд (эндпоинт включается переменной `SMS_STUB_OUTBOX=true`).
- Все телефоны - из диапазона `+7 900 000-00-xx`, люди и компании выдуманные.
- Ветка `case/b1`, PR, ревью подагентом.

## Решения исполнителя (обоснование - в REPORT)

- **Кто входит:** номер аутентифицирует **человека**. Один пользователь Keycloak на человека, `phone` - проверенный уникальный атрибут с датой проверки `phoneVerifiedAt`.
- **Где членство:** в Postgres приложения (`memberships`: человек × организация × роль × статус × даты), а не в Keycloak Organizations: роль и статус в конкретной компании, история увольнений и согласия - бизнес-данные, им нужны транзакции и аудит вместе с остальными данными приложения; Keycloak отвечает только за личность.
- **Активная организация:** выбирается после входа (`X-Org` в запросе) и **проверяется на каждом запросе** по `memberships`; токен короткий (5 мин). Отклонение от спеки («попадает в токен») - сознательное: проверка на API закрывает «уволен, а токен жив» независимо от токена; вариант с организацией в токене через Keycloak Organizations описан в отчёте как альтернатива.
- **Согласия:** `documents` (scope: `person` | `org`) → `document_versions` → `acceptances` (человек × версия × организация, `org_id` NULL для личных).
- **Переназначение номера:** если номер подтверждён давно (> 90 дней) и устройство новое - вход по одному SMS не даётся, нужен второй фактор (`step_up_required`).

## Review Focus

- Наивный realm должен ломаться **по-настоящему** (через тот же Keycloak и тот же API), а не потому, что тест так написан: каждый провал наивной модели виден в ответе Keycloak/API.
- Одноразовость и срок кода: повторное использование кода и код старше 5 минут отвергаются в обоих realm.
- Перебор кода: не больше 5 попыток на номер за 10 минут.
- Уволенный: отказ с первого же запроса после увольнения, даже со свежим токеном, выданным до увольнения.
- Согласие новой версии требует повторного принятия; принятие в A не засчитывается в Б.

### Task 2: Расширение Keycloak `keycloak-sms`

**Files:** Create `b1-phone-orgs/keycloak-sms/pom.xml`, `src/main/java/dev/aec/sms/{SmsCodeResourceProviderFactory,SmsCodeResource,SmsDirectGrantAuthenticator,SmsDirectGrantAuthenticatorFactory,CodeStore}.java`, `src/main/resources/META-INF/services/*`; Test `tests/sms.test.ts`

**Interfaces:**
- `POST /realms/{realm}/sms/code` `{ phone }` → 204; код (6 цифр, TTL 300 с, одноразовый) кладётся в `SingleUseObjectProvider`; лимит 5 запросов кода и 5 неудачных проверок на номер за 10 минут.
- `GET /realms/{realm}/sms/outbox?phone=` → последний код (только при `SMS_STUB_OUTBOX=true`).
- Direct grant: `POST /realms/{realm}/protocol/openid-connect/token` с `grant_type=password`, `client_id=app`, `phone`, `code`, `device_id`.
  - realm attribute `smsMode=naive`: первый пользователь с атрибутом `phone` (как в типичной первой реализации).
  - `smsMode=fixed`: ровно один пользователь с `phone` и `phoneVerified=true`, иначе ошибка `ambiguous_phone`/`unknown_phone`; если `phoneVerifiedAt` старше 90 дней и `device_id` не в атрибуте `knownDevices` → ошибка `step_up_required`.

- [ ] **Step 1:** Тесты (против стека): код выдаётся и принимается, токен содержит `sub` нужного пользователя; повтор того же кода → `invalid_grant`; неверный код 6 раз → лимит; код после TTL (TTL уменьшается переменной `SMS_CODE_TTL_SECONDS` для теста) → отказ.
- [ ] **Step 2:** Падают. **Step 3:** Реализовать, `mvn -q package`, пересобрать стек. **Step 4:** Зелёные. Commit `feat(b1): keycloak SPI - SMS code endpoint and direct grant authenticator`.

### Task 3: API и данные

**Files:** Create `b1-phone-orgs/src/{api,db,seed,naive,fixed}.ts`; Test `tests/api.test.ts`

**Interfaces:**
- `startApi({ mode: 'naive'|'fixed', port })`; маршруты: `GET /orgs/:org/data` (доступ к данным компании), `POST /orgs/:org/consents/:doc/accept`, `POST /admin/orgs/:org/members/:person/fire`, `POST /admin/persons` (заведение человека с телефоном), `POST /admin/phones/reassign`.
- naive: доступ по атрибуту `org` пользователя Keycloak из токена; согласие хранится по номеру телефона без версии и без организации; увольнение = отключение пользователя Keycloak этой компании.
- fixed: доступ - только при активном членстве в `memberships` (проверка на каждом запросе) и `iat` токена позже `revoked_before` для (человек, организация); согласие - по `(person, version, org)`, требуется последняя версия документа; увольнение = статус `fired` + запись в `revoked_before` + отзыв сессий пользователя в Keycloak через Admin API; заведение человека с занятым номером → 409.
- `seed(mode)`: один человек «Анна» с номером `+79000000001`, членство в 5 компаниях (A-E); в naive - 5 пользователей Keycloak с этим номером.

- [ ] **Step 1:** Тесты API на стеке: без токена 401; чужая подпись 401; член A получает данные A; не-член - 403.
- [ ] **Step 2-4:** Падают → реализовать → зелёные. Commit `feat(b1): API with naive and fixed access rules`.

### Task 4: Сценарии

**Files:** Create `b1-phone-orgs/tests/scenarios.test.ts`, `results/scenarios.json` (генерируется)

Каждый сценарий выполняется на обоих realm; тест проверяет, что наивная модель ведёт себя плохо (репро), а исправленная - правильно. Итог по сценариям пишется в `results/scenarios.json`.

- [ ] **S1. Вход по номеру:** Анна входит по SMS. naive: токен выдан пользователю одной из 5 компаний, выбранному Keycloak (не тому, куда она шла), доступ к остальным четырём - 403. fixed: токен человека, доступ к любой из 5 по `X-Org`.
- [ ] **S2. Уволена из A, осталась в Б:** токен получен до увольнения. naive: этим токеном A ещё открывается (200) до истечения токена. fixed: A - 403 с первого запроса, Б - 200.
- [ ] **S3. Согласие из A «переезжает» в Б:** принято в A. naive: Б считает согласие принятым. fixed: Б требует принять.
- [ ] **S4. Новая версия согласия:** опубликована v2. naive: старое «принято» действует. fixed: доступ к функциям, требующим согласия, - после принятия v2.
- [ ] **S5. Номер переназначен оператором:** новый владелец получает код на тот же номер с нового устройства. naive: входит в аккаунт Анны. fixed: `step_up_required`.
- [ ] **S6. Второй человек с тем же номером:** naive: заводится, вход неоднозначен. fixed: 409 при заведении.
- [ ] Прогон, `results/scenarios.json`, commit `test(b1): six phone/org scenarios on naive and fixed models`.
